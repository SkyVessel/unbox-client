# Minecraft 朋友联机客户端：产品功能与交互文档

版本：0.1 评审草案｜日期：2026-10-05｜状态：等待产品负责人评审

本轮交付是功能和交互规则，不是 UI 设计，也不是已经实现的产品。本文不确定页面布局、配色、字体、视觉风格或技术框架。按钮名称是解释流程的工作文案，可在下一阶段调整。

配套文档：[技术调研与可行性](./02-技术调研与可行性.md)、[需求闭环检查与待确认决策](./03-需求闭环检查与待确认决策.md)。文中的“建议”“目标”均不是已获批准的决定或实测结果。

## 1. 产品要解决什么问题

让不懂 Java、模组加载器、端口映射和服务器配置的人，也能和朋友稳定地玩大型 Java 版模组整合包。房主负责选择玩法；朋友点邀请、确认准备环境，即可进入同一个世界。

四个核心卖点：

1. **流畅地玩**：自动匹配经过验证的优化组合，判断卡顿来自画面、内存、服务器还是网络，并提供能撤销的调整。
2. **边玩边改**：通过游戏内 AI 对话制作轻量扩展，支持的功能在当前会话中生效；超出能力时说明需要重载或重启。
3. **邀请就能联机**：自动处理连接路径、房间权限、启动服务和重连，不要求朋友配置网络。
4. **大家用同一套玩法**：共享版本化的整合环境，自动处理模组、依赖和必要配置，同时保留各自的画质、按键和 HUD 偏好。

这些是产品的重点差异化方向，**不是已证明市场上不存在的独占能力**。现有产品已分别提供优化、邀请联机和整合包管理；我们的价值在于把这四件事形成可恢复的一条流程。

## 2. 已知要求、草案假设和范围

### 2.1 已知要求

- 支持大型模组整合游玩，以联机和共享环境为核心。
- 包含 FPS、Freelook、准星定制、粒子调整等游戏内体验功能。
- 支持 AI 经 MCP 管理客户端、游戏、模组与服务器规则。
- 保留正版身份与离线身份在允许此模式的自建房间内共同游玩的需求。
- 可以使用用户 Cloudflare 账号的免费额度；不能由此推导出允许付费。
- 本轮先写文档，检查未闭环需求；UI 设计等用户下一轮通知。

### 2.2 为使草案可评审而采用的假设

| 项目 | 草案默认 | 尚未确定的部分 |
|---|---|---|
| 游戏版本类型 | Minecraft Java Edition | 不把 Bedrock、手机、主机跨端列入首发 |
| 用户规模 | 先验证 2–8 位朋友、私密房间 | 这是测试范围，不是 Minecraft 固有玩家上限 |
| 操作系统 | Windows、macOS、Linux 为产品目标；建议 Windows 首发 | 用户设备构成、Apple Silicon 和 Linux 首发范围 |
| 游戏与加载器 | 根据目标整合包锁定版本；首发只认证有限组合 | 不宣称所有 Minecraft / Fabric / Forge / NeoForge 组合可用 |
| 房间形态 | 房主电脑开世界为主，本机独立服务为补充 | 是否首发要求房主退出游戏后仍可玩 |
| AI | 外部 MCP 助手与游戏内助手共用能力 | 模型提供商、费用、是否提供默认模型 |
| 数据 | 世界默认在房主电脑，本地备份 | 云存档和异地备份另定，不能假定免费不限量 |
| 商业模式 | 未定 | 影响上游许可、运行成本与账号体系 |

### 2.3 首版必须排除的隐含承诺

- 不保证任何 JAR 模组都可以热插拔；普通模组增删改通常需要重启。
- 不保证任何网络都能免费连接成功；直连失败需要实际可用的中继。
- 不保证所有电脑固定翻倍 FPS，也不把减少画质后的增益说成同画质优化。
- 不自动把客户端模组目录变成可运行的服务器包。
- 不承诺在 Cloudflare Workers 上运行常驻 Java 游戏进程。
- 不让离线账号伪装成正版身份，或进入要求正版认证的第三方服务器。
- 不把服务器插件、客户端模组、数据包视为可互换的文件类型。

## 3. 用户看到的概念与权限

### 3.1 少量必要概念

| 用户名称 | 实际含义 | 用户何时需要理解 |
|---|---|---|
| 世界 | 游戏存档 | 选择在哪个世界玩 |
| 房间 | 一次或持续存在的朋友联机会话 | 邀请、加入、结束联机 |
| 玩法包 | 固定版本的模组、依赖及共享设置 | 选择玩法、查看房主更新 |
| 小功能 | 由本客户端托管的轻量扩展 | AI 制作、启停和撤销 |
| 我的偏好 | 个人画质、按键、声音、HUD 等 | 调整自己的体验 |
| 恢复点 | 一套可恢复的环境或世界备份 | 更新失败或误改后恢复 |

“房间”不等于“服务器一直开着”，“共用玩法包”不等于共用同一个文件夹，“环境恢复点”也不等于可以无损倒退世界进度。

### 3.2 角色

| 角色 | 可以做什么 | 不可以做什么 |
|---|---|---|
| 房主/世界所有者 | 邀请、移除成员、发布玩法包、改共享规则、备份恢复 | 不因房主身份获得朋友电脑任意文件权限 |
| 协作者 | 默认可提出改包与规则方案 | 默认不能发布变更、重启或恢复世界；额外权限由房主授予 |
| 成员 | 加入、同步、修改个人偏好、创建个人小功能 | 不能私自改变共享规则或其他人的配置 |
| AI 助手 | 在当前用户授权范围内查看和操作 | 不获得独立管理员身份，不自动扩大权限 |

多人同时编辑共享玩法时产生草案。发布以当前版本为前提；版本已经变化时重新计算差异，不进行最后写入覆盖。

## 4. 全产品交互规则

1. **默认只做用户当前要做的事。** 接到邀请直接进入房间准备流程，不要求先学习模组管理。
2. **自动推导技术设置。** Java、加载器、文件路径、网络路径由系统处理；只有无法推导时才询问。
3. **把连续操作合成一次任务。** 例如“准备并加入”覆盖检查、下载、校验、启动、连接。可随时取消。
4. **说明变更范围与生效时间。** 固定使用“只影响我 / 影响全房间”和“立即 / 需要重载 / 下次启动”表达。
5. **显示真实进度。** 下载展示字节数；启动展示阶段。没有可靠估算时不显示虚假百分比或倒计时。
6. **失败后给下一步。** 用“缺少一个文件，点击补齐”代替只显示异常堆栈；技术详情可展开。
7. **重试不重复产生副作用。** 同一发布、下载、备份和 AI 应用任务均有任务标识。
8. **可逆的个人设置即改即看。** 不为每个滑块反复确认。执行共享影响或不可逆操作前显示一次明确摘要。
9. **默认配置足够可用。** 普通用户不需要在十几个性能模组选项中做选择。
10. **所有快捷操作有普通入口。** 不记命令也能使用；键盘操作、可读状态和文字反馈在下一阶段设计中必须保留。

正常流程的目标：已安装并完成身份设置的朋友，在可信房间首次加入时最多作两次主要决定；已信任且环境无变化的回访只需一次“加入”。首次系统权限、授权下载、登录、磁盘不足等例外单独记录，不藏在“真正一键”的宣传里。

## 6. 身份、安装与启动流程

### 6.1 首次使用

入口可以是客户端或朋友邀请。先识别邀请对应的玩法和房间，再进行必要的身份设置。默认建议微软登录；如果房间允许离线身份，可以选择本地身份并设置昵称。

系统自动检测系统架构、可用内存、图形能力、磁盘空间和所需 Java。首次准备前只展示预计下载量、安装位置和身份状态。空间充足使用默认位置；不足时提供“换位置”。

用户确认后进入可取消任务。取消保留已校验下载缓存，不留下可被误启动的半成品。启动时再次校验运行条件，故障恢复接回同一个房间，不让用户重新输入邀请码。

微软登录使用官方认证流程，不收集微软密码。令牌保存在系统凭据库，不进入玩法包、分享清单或 AI 上下文。会话失效时要求重新登录；不静默把正版房间降级为离线模式。

### 6.2 混合身份联机的产品规则

用户所说“盗版和正版一起玩”，本草案落实为：**允许离线身份的私密自建房间，可以接纳正版验证成员和离线成员**。产品仍须遵守游戏获取和使用条款；技术可连接不等于获得游戏使用授权。官方游戏文件从授权来源获取，不随客户端或玩法包二次打包分发。依据见 [Minecraft EULA](https://www.minecraft.net/en-us/eula)。

| 房间模式 | 正版验证身份 | 离线身份 | 规则 |
|---|---|---|---|
| 正版验证房间 | 可进入 | 不可进入 | 正常验证失败时提示重新登录 |
| 混合身份私密房间 | 可进入 | 经邀请可进入 | 需要本产品身份与服务端校验组件 |
| 第三方服务器 | 按对方要求 | 仅对方明确允许时 | 不更改对方认证或规则 |

混合模式不能仅靠昵称白名单：

- 本产品身份 ID、已验证正版 UUID、世界内玩家 UUID 分开保存。昵称仅用于显示。
- 离线身份先与设备凭据绑定；接受邀请后绑定房间成员记录。恢复与换机需要已有设备或房主重新授权，不凭相同昵称找回。
- 房主与管理员权限绑定稳定身份，不能通过改名取得。
- 同名成员要求改显示名或明确区分；不共享背包、领地、进度。
- 离线身份后来关联正版时，预览背包与 UUID 迁移，在停止写入和备份后操作。双方已有数据时不自动合并。
- 邀请校验必须在实际游戏连接入口执行，后端不能存在绕过该检查的开放路径。
- 正版身份验证、签名聊天、皮肤和第三方鉴权模组可能与混合模式不兼容；逐版本验证后才能标记支持。

身份映射协议仍待技术验证。未通过前，混合房间标为实验性，不以“已支持全部整合包”发布。

### 6.3 环境管理与导入

一个玩法对应一个独立环境；同一玩法的不同发布版本有独立记录。共享只读下载缓存可以节省磁盘，可写配置必须独立，避免硬链接导致修改污染其他环境。

导入顺序：识别格式 → 识别游戏/加载器/依赖 → 检查分发来源 → 展示缺失与冲突 → 建立副本 → 试启动 → 保存可用记录。

P0 支持 Modrinth `.mrpack` 和经授权可获取文件的 CurseForge 整合包；任意 ZIP 不能都当作整合包。已有目录导入只复制选中的游戏内容，不读取无关凭据和文件。无法识别的本地 JAR 显示“来源未识别”，允许仅本机使用，不自动分享给朋友。

新增、更新、禁用、删除模组首先生成变更计划。删除一个被依赖的模组时说明受影响内容，不自动连带删除用户存档。删除玩法默认保留世界备份，只有明确选择才删除世界数据。

## 7. 核心流程一：超级简单的联机

### 7.1 房主流程

1. 选择已有世界或新建世界；已有世界自动带出关联玩法。
2. 点击“邀请朋友”。系统检查环境可分享性、身份模式和电脑承载条件。
3. 第一次开放此世界时确认房间类型和成员访问规则。默认私密、按邀请加入；混合身份模式需明确开启。
4. 系统准备共享快照、启动世界与连接服务。只有服务健康且每个必要文件都有合法获取路径，才显示“可加入”。存在仅能手动获取的文件时，明确标记“加入前需要手动准备 X 个文件”，不能显示为全自动加入；任何必需文件没有合法获取路径时阻止发布。
5. 复制邀请或分享链接。朋友加入时显示真实阶段：准备环境、启动中、连接中、已进入。

新世界可用系统默认名字和世界参数，不强迫填写服务器名称、IP、端口、Java 路径等。若朋友不能自动获取某个必要模组，发布前让房主选择可自动获取的替代项，或接受官方手动获取步骤；邀请预览说明该例外，不能等朋友下载到一半才第一次告知。

### 7.2 朋友流程

1. 打开邀请，展示房主、世界、玩法摘要及身份要求。未安装客户端时由下载入口安装并恢复邀请；无法自动恢复时可粘贴邀请码。
2. 首次确认“准备并加入”，展示下载量、共享代码来源、新权限和需要重启的情况。
3. 系统建立隔离环境，下载缺失部分并验证，启动正确游戏，提交加入凭证。
4. 服务端确认身份、当前房间版本和规则后允许进入。

邀请码失效、房间关闭、被移除、人数已满分别给具体结果。邀请码是领取入场权限的入口，不是永久管理员密码；建议默认 24 小时失效，可撤销。临时凭证仅用于本次连接，过期重新签发；云端不可用时不默认放开身份校验。

### 7.3 连接策略与回退

产品要求：本地局域网或可达直连优先，其次尝试 NAT 穿透，最后使用已验证可用的中继；用户看到“正在连接”，高级诊断才显示网络术语。底层方案尚未确定，必须完成实网原型。

不默认要求装 VPN、修改路由器、找公网 IP 或开放管理端口。防火墙必须授权时显示一次系统许可；被拒绝后说明如何恢复。

30 秒仍未连通的草案阈值触发诊断，不无限旋转：显示“直连未成功，正在尝试备用连接”；没有可用中继时明确“此网络目前无法连接”。不把免费额度不足伪装成用户网络故障。

连接中断时保留成员和环境，有限次数自动重试并显示倒计时；用户可立即停止。连接路径切换可能要求重新连接，不能承诺所有中断都无感。

### 7.4 房主退出、休眠和换人

| 情况 | 用户反馈 | 系统行为 |
|---|---|---|
| 房主退出正在共享的游戏 | “退出后朋友也会断开” | 保存世界、停止接纳、通知成员、关闭连接 |
| 房主仅关闭启动器窗口 | 显示后台状态 | 已运行的游戏与必需连接服务继续；完全退出需明确结束房间 |
| 电脑休眠、关机或断网 | 成员看到房主离线 | 尽力保存，停止承诺可加入；恢复后验证世界与房间状态 |
| 本机后台服务器运行 | “游戏已退出，房间仍在运行” | P1；电脑须保持开机和联网 |
| 换朋友接管 | “准备交接世界” | P1；停写、快照、校验、接管后旧端只读，失败保留旧房主 |
| 希望全天候在线 | “需要一台持续运行的设备” | P1 接入自有服务器；不把 Cloudflare 当作免费主机 |

游戏的暂停行为须适配多人共享，不能让房主切出窗口后把所有人暂停。建议共享时允许系统防休眠，但由用户一次选择，结束后恢复。

## 8. 核心流程二：共用玩法与模组列表

### 8.1 共享的不是文件夹，而是可复现的版本

每个发布版本至少记录：游戏版本、加载器及版本、Java 要求、模组来源与精确文件版本、哈希、依赖、客户端/服务端用途、配置策略、数据包/脚本/必要资源、客户端桥接组件版本、发布者和版本摘要。

Modrinth 格式已有下载地址、文件哈希和环境区分；本产品在其上补充房间权限、配置策略与发布生命周期，不把自定义字段伪装成标准字段。见 [Modrinth 格式说明](https://support.modrinth.com/en/articles/8802351-modrinth-modpack-format-mrpack)。

| 内容类型 | 谁决定 | 同步行为 |
|---|---|---|
| 共享玩法必需项 | 房主发布 | 精确版本与哈希必须满足 |
| 服务端专用内容 | 房主发布 | 只装服务端；成员知道其存在但不安装 |
| 客户端必需桥接/玩法项 | 房主发布 | 所有成员安装匹配版本 |
| 个人可选体验项 | 成员选择，受规则限制 | 允许不同；不能改变房间玩法协议 |
| 共享规则和必要配置 | 房主发布 | 按字段或文件策略锁定；加入前验证 |
| 画质、声音、按键、HUD | 各成员 | 不从房主覆盖 |
| 凭据、日志、截图、私人地图标记 | 各成员 | 不随玩法包共享 |
| 世界存档 | 世界所有者 | 普通加入不下载整份存档；交接另走流程 |

未知配置不能一概同步，也不能一概忽略。采用已知适配规则；未分类且可能影响玩法的文件进入房主发布前检查。用户确认其用途后固定策略；AI 只能建议分类，不能凭文件名保证安全。

### 8.2 发布与更新

房主编辑 → 草案 → 依赖与冲突检查 → 下载可达性/权限检查 → 测试环境启动 → 变更摘要 → 发布不可变版本。

房间指向明确版本，成员加入时绑定这一版本。下载中若房主发布新版，不混用两个版本：先完成当前任务，再根据服务端仍在运行的版本决定继续或切换。

| 变更 | 生效策略 |
|---|---|
| 自己的 HUD、准星等 | 本地立即生效，不生成共享玩法更新 |
| 经验证的轻量共享扩展 | 按第 10 章协调发布；不属于普通 JAR 热插拔 |
| 需重载的数据规则 | 房主选定应用时机，通知在线成员并验证 |
| 普通模组增删改、加载器/游戏升级 | 默认下次开房生效；房主也可明确安排停服维护 |

朋友默认跟随房间的已发布版本，看到“新增 2 个模组，需要下次启动安装”等简明摘要。首次信任后可自动准备无新增权限的版本；增加文件/网络等权限或更换未知代码来源时重新展示风险和来源。拒绝必需更新可保留自己的旧环境，但不能以不匹配环境进入新版房间。

### 8.3 下载、同步与冲突恢复

- 文件先下载到暂存区，校验通过后一次性切换；失败继续使用原可用环境。
- 相同哈希复用缓存，更新只下载变化文件，支持断点续传和取消；原站是否支持续传须检测。
- 自动分析已声明依赖、版本、重复模组和已知冲突；未知运行时冲突靠试启动发现，不宣称静态分析覆盖全部问题。
- 房主包缺少服务端版本时，阻止“独立开服”，提供验证后的服务端清单，不直接移除一堆文件碰碰运气。
- 成员手动改了受管理文件时，提供“恢复房间版本”或“另存为个人玩法”；保留副本。
- 任意本地文件上传或转发需有分发依据；受限模组引导到官方允许的获取流程，系统校验后继续。
- 上游文件下架且无合法缓存时标为不可安装；房主更换依赖并重新发布。不能从未知镜像默默替换同名文件。

### 8.4 环境回退与世界回退

环境回退恢复模组和配置；世界回退恢复游戏进度，二者必须分开。涉及内容模组、世界生成或格式升级时，在世界副本验证后再运行正式世界。新版本已经写入世界后，禁止把旧模组版本直接套回当前世界；应选择匹配恢复点，并明确会回到何时的进度。

## 9. 核心流程三：性能优化

### 9.1 用户交互

默认使用“自动推荐”。仅提供少量意图明确的档位：“更流畅”“平衡”“更好看”。这些档位如何影响画质必须可见；调低视距、粒子、光影时说明具体变化。

用户点击“检查卡顿”或对 AI 说“刚才很卡”。系统按需采集短时间性能信息，给出最可能原因和证据：画面渲染慢、内存压力、服务端运算慢或连接不稳。数据不足时明确“尚不能判断”。

系统提供“应用建议”，显示改动、影响范围和是否重启。完成后在可比场景下观察，显示改善、无明显变化或变差。保留“一键恢复”。不在玩家战斗中自行反复修改画质。

### 9.2 优化功能清单

| ID | 功能 | 交互与边界 |
|---|---|---|
| P01 | 认证优化组合 | 根据版本/加载器/显卡选组合；已有同类模组不重复安装 |
| P02 | 渲染与粒子优化 | 稳定优化默认启用；影响画质的调整可预览和恢复 |
| P03 | 内存与 Java 配置 | 使用匹配运行时与保守参数，给系统及本机服务器留余量 |
| P04 | 启动耗时优化 | 缓存和增量校验；展示各阶段耗时，无法省略的加载如实显示 |
| P05 | 后台资源控制 | 切后台时降低不必要渲染；房主服务端不能随之降速或暂停 |
| P06 | 卡顿诊断 | FPS、帧时间、GC、TPS/MSPT、延迟分开解释 |
| P07 | 启动器自身性能 | 游戏运行后减少动画、扫描与轮询，后台下载/编译可暂停 |
| P08 | 高级实验优化 | P1，逐项 opt-in；不混入默认稳定配置 |

调研候选包括 Sodium、Lithium、FerriteCore、ImmediatelyFast、ModernFix、Entity Culling、Dynamic FPS 和 spark。它们处理不同瓶颈，不能把名单全部无条件叠加。原理、来源和许可约束见[调研第 2 节](./02-技术调研与可行性.md)。

针对用户“继续改造其逻辑”的要求：先测瓶颈，再在许可允许的前提下做上游贡献、适配或自研补充。不能把阅读到源码等同于可以复制到闭源商业客户端；也不能在没有基准的情况下承诺比成熟优化组合更快。

### 9.3 性能验收建议

使用固定世界、路线、分辨率、视距、光影、模组版本与电源条件；预热后至少重复 3 次，报告中位数和波动。分成原始整合包、成熟优化组合、加入本客户端三个基线。

记录平均 FPS、1% low、p95/p99 帧时间、超过 100 ms 的帧数、峰值内存、启动时间、服务器 p95 MSPT 和网络延迟。服务器有组件时读取真实 TPS；没有组件时必须标成估计。

**待批准的研发目标**：认证低/中档设备上，相较未优化的同一整合包，平均 FPS 提升至少 30%、1% low 提升至少 20%；对于原本已优化的整合包不承诺同等提升。加入本产品桥接/HUD后的平均 FPS 退化不超过 3%，帧时间长尾不明显恶化。若不能达到，公布适用场景和实际值，不能用降画质结果充数。

这些数字用于筛选方案，尚无测试证明。支持设备和参考整合包未选定前，不能作为对外保证。

## 10. 核心流程四：AI 制作与热加载

### 10.1 三种生效能力

| 类别 | 例子 | 用户标签 | 交付规则 |
|---|---|---|---|
| A：受控轻量扩展 | HUD、准星样式、提醒、计时、输入快捷入口、已支持的粒子显示参数 | 立即生效 | 由专门运行时管理；支持停止和撤销 |
| B：资源/数据重载 | 纹理、部分声音、适用版本的配方/标签/战利品规则 | 需要重新载入 | 可能有短暂停顿；某些变化还需重进世界 |
| C：普通模组与底层变更 | 任意 JAR、Mixin 注入、渲染引擎更换、新注册物品/方块/实体等 | 需要重启 | 生成项目或待安装包，下次启动应用 |

分类依据是实际能力清单和目标版本测试，不是 AI 觉得“代码很简单”。“改动小”不等于“可以热加载”。KubeJS 也区分可重载脚本与需要重启的注册行为，见[官方说明](https://kubejs.com/)。

### 10.2 一条完整创作流程

例子：玩家说“血量不足四颗心时，在画面边缘闪一下，并且可以关闭”。

1. 游戏内助手读取当前玩家可用状态、扩展 API 版本及服务器规则，不把问题发到公共聊天。
2. 给出结果摘要：“只影响你；低于四颗心时显示提示；可立即使用。”缺少关键条件才追问。
3. 在隔离任务中生成源文件、扩展清单、使用的能力和验证结果。编译不能占用游戏主线程。
4. 检查 API、权限、资源预算和可卸载性；预览尽可能在模拟数据中完成。
5. 玩家点击“试用”，运行时载入草案，默认 30 秒后恢复；玩家选择“保留”或“撤销”。此时长是可调整的产品默认。
6. 保留后保存版本历史及停用入口。错误自动停用新版本并恢复旧版本；崩溃后下次启动隔离该版本。

若需求是“增加一个有新 ID 的矿石”，助手应交付需重启的模组计划/构建产物，而不是谎称热加载成功；玩家可稍后完成安装，不中断当前游戏。

### 10.3 首发支持的轻量能力范围

- 读取允许的玩家状态：血量、饥饿、坐标、背包摘要、当前场景和公开性能数据。
- 使用规定的绘制组件显示文本、图标、条形、准星与简单提示。
- 注册可管理的按键、计时器和事件回调；按键冲突给出替代。
- 改变本产品暴露的显示参数；不任意反射访问游戏内部类。
- 保存扩展自身少量设置；不能遍历用户目录。
- 服务端规则通过独立的房主权限接口执行，不由客户端脚本直接改世界。

默认无任意文件、网络、系统进程、原生库和 Java 反射访问。若业务需要超出沙箱能力，转为普通模组开发流程。KubeJS 或普通 JVM 类加载器不能直接当成可信安全沙箱；运行时选型须验证隔离和可中止能力。

### 10.4 热加载生命周期

草案 → 验证 → 预加载 → 暂停旧回调 → 迁移可兼容状态 → 切换 → 健康检查 → 生效。

每个扩展拥有自己的监听器、计时器、绘制项和状态，由宿主登记并回收。无效版本不触碰旧实例；切换失败恢复旧版本。超出执行预算的扩展可被中止并隔离；仅捕获异常不足以处理死循环，因此不能让未知代码直接在游戏主线程无限执行。

移除扩展必须注销回调、释放资源、删除显示，不遗留重复触发。状态迁移不兼容时提示重置扩展状态，不悄悄重置玩家世界。

### 10.5 全房间发布

个人显示扩展不要求别人安装。改变共享玩法的扩展由房主发布；涉及客户端协议时，所有当前成员先准备并确认兼容，服务端再切换规则版本。在短时等待窗口内拒绝不兼容的新加入。

任一成员准备失败，默认维持旧版本并提示原因；房主可安排下次维护，不强制把玩家踢掉来冒充成功。网络分区下不宣称瞬时全员原子切换：服务端按激活版本校验，重连成员同步后再进入。

已经执行的世界行为通常不能通过卸载代码撤销。比如规则已经发放物品、破坏方块，回退代码不会逆转这些行为；此类任务须在测试世界验证并提供合适备份。

## 11. AI、MCP 与服务器规则

### 11.1 两种 AI 入口

**游戏内**：用户打开助手或输入本地命令 `/ai 帮我做一个低血量提醒`。该命令由客户端消费，不能被误发送到服务器公共聊天。游戏内对话可以暂停、取消、撤销和查看具体改动。

**外部助手**：设置中点击“连接 AI”，生成本机配对配置。支持 MCP 的助手完成配对后，可以操作被选择的环境和房间。MCP 是工具协议，不提供模型推理，也不意味着任何聊天应用都自动支持连接。

没有模型时，所有联机、同步和手动设置仍可用。助手说明尚未连接，可选用户已有 API 或外部助手；不因为“Cloudflare 免费”就承诺无限免费代码生成。

本地可读取的数据不等于允许发送给外部模型。首次连接模型时说明提供商和默认上下文：用户当前请求、目标环境版本、可用能力，以及完成本次任务所需的本人状态摘要。坐标、背包详情、世界内容、源码或日志仅在相关任务需要时纳入，并可查看和取消；不默认发送完整存档、公共聊天记录或其他玩家的私人数据。模型凭据存系统凭据库；用户可清除本地对话记录，但外部提供商的数据保留遵循其服务政策，不能承诺本地删除等于外部删除。

### 11.2 MCP 能力目录（产品契约草案）

| 能力组 | 只读能力 | 写入能力及权限 |
|---|---|---|
| 客户端 | 列环境、版本、运行状态、健康检查 | 启动/停止指定环境；停止游戏需保存提示 |
| 模组 | 搜索、列清单、依赖/冲突分析、比较版本 | 生成草案、测试；房主权限才能发布共享版本 |
| 游戏 | 读取允许的玩家/世界摘要、性能 | 修改自己的可用体验设置；共享规则走服务端权限 |
| 扩展 | 能力清单、日志、源码和版本 | 生成、测试、试用、停用、回滚指定扩展 |
| 房间 | 成员、连接质量、共享版本 | 邀请/撤销/移除；仅授权房主或协作者 |
| 服务器 | 状态、规则、备份列表 | 规则草案、验证、应用、重启和恢复；按动作授权 |
| 诊断 | 脱敏崩溃摘要、有限日志 | 生成修复草案；不默认上传全部文件 |

工具以明确资源 ID、预期版本、影响范围和任务 ID 工作。返回“未执行/运行中/成功/失败/已回滚”，长任务可查询与取消。不得用一个不受限的 `run_command` 代替全部能力。

本地连接优先 stdio 或带鉴权的回环地址；如采用 HTTP，校验来源、会话与目标。默认不暴露公网 MCP，不共享微软访问令牌。撤销配对后旧凭证失效。参照 [MCP 安全建议](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices)。

### 11.3 AI 应用规则

AI 的回答必须说明：改哪里、影响谁、何时生效、需要什么权限、如何撤销。低风险个人偏好在用户已授权的任务中可直接修改并提供撤销；共享规则、安装新代码或重启需显示完整变更摘要。

世界聊天、模组说明、书本内容、日志和下载页面都是任务数据，不能作为授予权限的指令。成员让 AI 执行房主指令仍须失败。生成测试通过不等于任意代码安全，权限必须由运行时强制执行。

### 11.4 服务器开发和规则配置

支持三个层次：常用规则模板；自然语言生成可审查的配置/脚本；高级模式导出源码项目和构建产物。

例子：“关闭 PVP、开启死亡不掉落，其他不变。”系统读取现状，生成两项变更，检查是否能在运行时修改。房主确认后执行、回读验证，保存旧值；若服务器不支持实时修改，加入下次重启计划。

新配方、权限插件和复杂事件需要识别宿主：Fabric/Forge/NeoForge 模组服、Paper 插件服和原版数据包各自使用匹配方案。不能在普通模组服中直接安装 Paper 插件，也不把混合服务端列为默认解决方案。

AI 不能通过成员端绕过管理员权限；公开服务器上的规则修改只允许用户已拥有并授予的能力。

## 12. 内置体验功能

以下是本产品拟定范围，不是 Feather 完整功能复制表。Feather 页面证明其包含 FPS、Perspective/Freelook、准星、坐标、延迟等常见模块，并允许服务器禁用部分功能。参考：[Feather Mod Management](https://docs.feathermc.com/server-api/mods/)。粒子调整是用户明确提出的本产品需求。

| 功能 | 阶段与默认 | 用户交互 | 生效与异常 |
|---|---|---|---|
| FPS/帧时间/延迟显示 | P0，精简显示 | 开关、位置、字号；详细数据按需展开 | 即时；无数据时显示未知 |
| Freelook 自由视角 | P0，默认关 | 按住/切换模式，设置按键 | 即时；服务器禁用时说明原因 |
| 准星定制 | P0，默认原版 | 选预设，调大小、间距、颜色和透明度 | 即时预览，一键复原 |
| 粒子调整 | P0，默认保持玩法可辨认 | 数量、类别、强度的受控设置 | 即时或资源重载；不可隐去被规则要求的提示 |
| HUD 模块编辑 | P0 | 显示/隐藏、位置、缩放、恢复预设 | 保存个人偏好，不随共享包覆盖 |
| 坐标、方向、装备耐久、状态提示 | P0，默认精简 | 在 HUD 中选择需要的信息 | 即时；不具备可靠数据时不编造 |
| 缩放、视野调整 | P1，默认关 | 按键缩放或调整视野 | 遵守房间/服务器规则 |
| 按键冲突查找 | P0 | 输入功能名或按键，选择替代 | 即时；允许保留有意设置的组合 |
| 连续疾跑等辅助输入 | P1 | 开关与按键 | 不扩展为未经允许的自动战斗宏 |
| 聊天、通知、提示框整理 | P1 | 过滤显示、大小和声音；恢复默认 | 不擅自代发聊天 |
| 死亡点/私人标记 | P1 | 保存、显示、删除，主动分享 | 默认仅本地；服务器可限制 |
| 截图与资源包管理 | P1 | 本地保存、切换资源包 | 上传另行操作；重载时提示短暂停顿 |
| 好友语音 | P2 | 加入语音、静音、音量 | 单独评估端口、带宽和麦克风权限 |

服务端禁用是明确状态，不是灰掉无解释。自己的房间可管理功能策略；第三方服务器仅在有可靠规则接口时自动应用，否则使用保守预设并允许用户查看规则。客户端声明不能作为强反作弊保证。

## 13. 备份、故障与数据生命周期

### 13.1 备份要求

创建备份必须停写或使用经验证的服务端一致性保存流程，不能直接压缩正在写入的世界就宣布可靠。每个恢复点记录世界版本、玩法版本、时间、大小和校验结果，并保存恢复背包、进度、领地等数据归属所需的身份映射版本。备份不包含登录令牌或设备私钥。

恢复世界数据不能自动恢复历史成员授权。当前有效的移除、封禁、凭证撤销和管理员权限记录保持生效；恢复过程将历史玩家数据映射到当前已验证身份。历史权限文件与当前策略冲突时，先由房主核对，再开放房间；不能重新授予已撤销的 OP。身份映射缺失或无法证明归属时停止自动迁移，不凭昵称分配背包。

升级游戏/内容模组、世界交接、身份迁移、破坏性规则变更前建立备份。默认建议保留最近 5 个自动恢复点，用户固定的备份不自动删除；空间不足时先处理空间，不静默跳过必要备份。此保留策略待评审。

恢复时停服、锁定写入、验证快照，保留当前状态后恢复匹配环境。失败时保持服务关闭和可恢复状态，不自动把损坏版本设为当前世界。

### 13.2 必须设计的失败反馈

| 情况 | 面向用户的表达 | 恢复动作 |
|---|---|---|
| 磁盘不足 | “还需要约 X GB 空间” | 换位置或清理已确认的下载缓存 |
| 文件来源限制 | “这个模组需要从作者页面获取” | 打开允许来源、选择下载文件、自动校验 |
| 加载器冲突 | “这两个模组不能用于当前玩法版本” | 展示可用替换方案或取消变更 |
| 游戏已开着 | “这次更新需要重启游戏” | 稍后应用；或保存后重启并回到房间 |
| 热加载失败 | “小功能未启用，已保留旧版本” | 查看原因、让 AI 修复、删除草案 |
| 服务器版本不同 | “房间已更新，正在重新检查” | 绑定当前服务端版本，不直接重复连接 |
| 网络不可达 | “未找到可用连接，已保留准备好的环境” | 重试、查看替代连接方案 |
| 房主断线 | “房主暂时离线” | 等待有限重连或退出，不重新下载 |
| 云服务/额度暂不可用 | “房间服务暂不可用” | 保留本地单人和可维持的现有连接 |
| AI 超时或预算用尽 | “这次生成未完成，游戏不受影响” | 保存草案、改用已有助手或稍后继续 |
| 游戏崩溃 | “上次启动未完成” | 禁用最近扩展、恢复环境或在副本中诊断 |
| 恢复点损坏 | “这个备份未通过检查” | 选择其他恢复点，不覆盖当前世界 |

故障归因区分已确认与疑似。不能看到堆栈中的模组名就自动删除该模组，尤其不能用删内容模组的方式在正式世界反复试错。

### 13.3 数据保存和清理

世界与个人设置默认本地；云端只存房间、成员、玩法元数据和获准共享的文件。诊断日志默认本地保存 7 天，上传需用户选择并脱敏；此天数为建议。

普通断开游戏连接只结束本次会话，保留成员关系，回访可重新签发加入凭证。用户主动退出成员关系或被房主移除时撤销成员权限和未使用的加入凭证；移除当前在线成员同时断开其游戏连接。本地下载的合法模组和用户已持有的文件无法“远程收回”。删除云端玩法版本不立即删除仍被房间引用的文件。卸载客户端应允许保留世界和备份；不把“清理缓存”与“删除存档”混为一项。

## 14. Cloudflare 的使用边界

本轮只做资源方案，没有连接账号或创建资源。当前会话未发现可调用的 Cloudflare 管理连接器；账号实际计划、已有消耗和剩余额度尚未读取。

建议 Workers 处理邀请和 API，Durable Objects 处理房间实时协调，D1 存元数据，R2 仅存允许分发且受容量控制的小文件。游戏进程在房主电脑或自有服务器运行。免费额度、可用性与中继边界见[技术调研第 5 节](./02-技术调研与可行性.md)。

免费额度是上限，不是必须用完的预算。部署前需建立账号级预算：扣除现有项目使用量、保留安全余量、限制本产品调用和上传、可关闭新增任务。R2 等包含超额计费的产品，不能仅凭一个告警就承诺零账单；无法建立可靠限额时先不用该路径。

达到限制后可暂停新邀请、发布或云文件上传，但不删除世界、不自动开通付费计划。已直连的游戏会话尽量维持；需要云端续签或中继的连接可能中断，要分别说明。

## 15. 交互状态契约

| 对象 | 主要状态 | 允许的下一步 |
|---|---|---|
| 环境 | 未准备 → 检查 → 下载 → 校验 → 可启动 → 运行中 | 运行中不替换普通 JAR；失败回到原可用版本 |
| 房间 | 草案 → 准备中 → 可加入 → 维护中 → 已结束 | 服务健康前不能显示可加入 |
| 加入任务 | 验证邀请 → 身份 → 准备环境 → 启动 → 连接 → 已进入 | 任一步可取消；恢复时复用已完成阶段 |
| 玩法版本 | 草案 → 已验证 → 已发布 → 使用中 → 已归档 | 已发布不可原地修改；更新产生新版本 |
| 扩展 | 草案 → 已验证 → 试用 → 已启用 → 停用/回滚/隔离 | 失败不能显示成功；旧版可恢复 |
| AI 任务 | 理解需求 → 方案 → 生成 → 验证 → 待应用 → 应用 → 验证结果 | 取消必须停止尚未授权的后续操作 |
| 备份 | 准备 → 一致性保存 → 校验 → 可恢复 | 校验失败不能列为有效恢复点 |

应用成功必须通过运行中组件回报或回读验证，不能以“文件已经写入”“AI 说完成了”作为唯一证据。

## 16. 验收用例

所有数值为建议门槛，需结合最终测试环境确认。

| ID | 场景 | 可验证的通过条件 |
|---|---|---|
| A01 | 新朋友加入大型包 | 无手动编辑配置；全部必需项精确匹配；个人偏好保留 |
| A02 | 回访同一房间 | 一次加入；不重复下载已校验文件 |
| A03 | 下载中断/退出 | 重试可复用完成内容，原环境仍能启动 |
| A04 | 房主发布更新 | 在线玩家继续使用当前版本或进入明确维护流程，无混版加入 |
| A05 | 删除内容模组 | 阻止在原世界无备份试错，提供副本验证和恢复方案 |
| A06 | 混合身份 | 双身份能进入测试房间；改名不能冒领 OP、背包或领地 |
| A07 | 受限网络 | 覆盖双重 NAT、CGNAT、IPv6、防火墙与移动热点；报告各类成功率及中继比例 |
| A08 | 热加载正确性 | 预定义 20 个 A 类例子中至少 18 个无需重启可用，失败保留旧版 |
| A09 | 热加载稳定性 | 重复载入/卸载 100 次，无重复监听/定时任务和持续增长的残留资源 |
| A10 | 热加载隔离 | 死循环、超内存、非法文件访问被中止或拒绝，不冻结游戏 |
| A11 | 复杂模组生成 | 正确标记需要重启，不执行伪热加载 |
| A12 | MCP 权限 | 成员改共享规则被拒绝；撤销配对有效；聊天中的指令不能获得权限 |
| A13 | 性能 | 按第 9 节对照基准测量，披露画质变化和误差 |
| A14 | 世界恢复 | 备份恢复到对应世界/玩法/身份版本，无法验证的备份不覆盖原世界 |
| A15 | 免费额度 | 压测触发任务限额，无自动付费升级；无法验证账单约束的产品不上线 |
| A16 | 易用性 | 5 位没有开服经验的测试者中至少 4 位无需口头指导完成邀请和加入 |
| A17 | 服务退出 | 房主退出、关机、休眠、网络中断显示不同原因且可恢复 |
| A18 | 共享扩展更新 | 成员离线、准备失败、服务端切换失败均不能造成未解释的规则版本混用 |

“大多数简单模组可热加载”的测量分母固定为公开列出的 A 类任务集，不把所有 Minecraft 模组混入统计，也不只选一个成功演示代表全部。

## 17. 分期与进入 UI 设计前的条件

**阶段 0：需求确认与高风险原型。** 选目标整合包与设备；验证热加载可中止、混合身份映射、真实网络连接和共享包分发。先确认能支撑产品承诺。

**阶段 1：P0 联机闭环。** 完成身份、环境、邀请、共享包、稳定优化、核心体验模块、有限热加载、AI/MCP、规则、备份与故障恢复。可以分批内测，但最终 P0 验收必须覆盖四个核心点。

**阶段 2：P1 扩展。** 增加认证加载器/平台，本机后台服务器、远程连接器、世界交接和更多体验模块。

**阶段 3：P2 候选。** 语音、云备份、公开内容市场按实际需求和成本再决定。

下一轮 UI 设计以本文的任务和状态为输入，先覆盖首次加入、回访加入、房主邀请、更新失败、热加载试用/撤销、AI 权限、备份恢复等关键状态。视觉美观由下一轮方案和实际评审验证，本轮不凭文字宣称已经保证。

进入 UI 前优先决定：目标整合包与平台、离线身份范围、房主退出行为、首发热加载边界、中继可接受的成本与失败策略。完整问题及建议见[需求闭环检查](./03-需求闭环检查与待确认决策.md)。
