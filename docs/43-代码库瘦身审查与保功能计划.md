# 代码库瘦身审查与保功能计划

日期：2026-10-19。对象：当前工作区，包括未提交的 10 月 18–19 日功能与披风修复。

本轮只检查和汇报，没有删除、重构产品代码，没有清理磁盘、更新现用应用或发布版本。运行了现有本地测试、前端构建和离线资源检查；构建与测试会更新忽略的输出目录。

## 结论

存在可以明确收缩的旧实现和不可达界面，但当前架构不需要推倒重写。最有价值的顺序是：删除确定不用的路径 → 分离测试交付 → 收拢重复事实 → 按测量结果优化运行开销。

“功能不丢失”应定义为保持现有可达功能及其数据兼容、权限、恢复行为；不能承诺所有历史需求已实现，也不能用本轮 Node/Rust 测试替代六组真实游戏回归。

## 3. 高置信度清理对象

- `main.tsx:19` 旧 16 项模块数组。
- `moduleOpen/activeModule`、旧模块弹窗、仅供它使用的 `setConfig` 路径和图标导入。

注意：`mod-options.json` 目前仍被 `model.ts` 用于生成新 Profile 默认配置；`saveModules` 仍在创建 Profile 时写配置。不能跟随弹窗一起直接删除。可在第二步导出“默认值专用数据”，再评估是否移除前端完整设置目录及启动器侧配置镜像。

CSS 字符串扫描只提供候选，不能处理全部动态拼接和公共选择器。清理后检查普通窗口、小窗口、全屏及三个现有页面，不按扫描结果整段盲删。

## 5. 重复事实与重复逻辑

### 版本与加载器矩阵：优先合并

NeoForge 精确版本映射至少重复在：

- `src-tauri/src/versions.rs:3`
- `scripts/build-neoforge-mod.py:6`
- `scripts/build-status-effect-bars.py:13`
- `scripts/benchmark.py:10`
- `scripts/prepare-game-runtime.py:22`

前端 Profile 类型/选项、云端允许列表、资源校验脚本还各自维护游戏版本集合。建议建立一份小的版本清单，构建时生成不同语言的常量或直接读取，并用一致性检查阻止漏改。各语言不必引入一个通用运行框架。

### 托管模组名单与共享协议：合并规则来源，保留两端验证

`EnvironmentManifest.java:10–11` 与 `sharing.rs:6–15` 重复托管 ID、单文件 512 MiB、总量 4 GiB、512 文件上限及资源选择规则。新增模块需要人工同步。

建议共同维护协议常量、托管 ID 来源和一组有效/无效 manifest fixture，两端各自运行同样的验收样例。Java 收包验证和 Rust 写入验证发生在不同边界，不能只留一端。不要移除哈希、路径、身份和文件保护检查来追求行数下降。

### 模组设置数据：延续已有单一来源，去掉旧镜像职责

`ModOptions.java` 已经是游戏设置目录，`scripts/export-mod-options.py` 生成 JSON，`tests/mod-catalogue.test.mjs` 校验源码摘要。这部分已有正确方向。

问题是旧启动器仍另存模块名称/分类目录及状态镜像。先移除不可达界面，再让新 Profile 初始化读取最小默认值数据；不要再建第三套设置描述。各原生模组的配置适配与权限控制应保留。

### 文件与网络助手：只收敛语义相同的部分

`content.rs:4`、`launcher.rs:20/149` 与 `sharing.rs:5` 有多种文件摘要实现；其中一些整体读入文件，另一些分块读取。可以统一分块摘要助手，保持调用方各自的算法、大小上限和安全校验。

`main.rs:22` 与 `social.rs:22` 都叫 atomic，但后者具有随机临时文件和 Unix 0600 权限，前者还负责父目录创建。它们不是可以机械替换的同义函数。合并前要明确保密权限、覆盖语义、失败清理及 Windows 行为。

`content.rs`、`launcher::jar_mod_ids` 和 `sharing.rs` 对 JAR 的读取职责有交集。适合共享元数据解析原语；展示信息、安装冲突识别、共享包准入仍保留各自策略。

### 依赖版本重复：后排处理

`cargo tree` 确认应用直接使用 reqwest 0.12.28，`tauri-plugin-updater` 使用 0.13.5。可在独立依赖升级中验证是否统一；这不是本轮可直接删掉的依赖。不要为了减少一个重复版本同时重构账号网络与更新链路。

Fabric/NeoForge 的 `Platform/MapTransport/LoginTransport` 是必要的原生适配层。152 个 Java 源文件中已经大量共用主目录源码，继续保持。六个 JAR 不能合成一个运行时转换包；`ports/` 中未直接发布的平台目录也可能被上游预处理/构建引用，不按名称删除。

## 6. 测试应分离交付，不能当垃圾删除

当前 `build-mod.sh` 与 `build-neoforge-mod.py` 编译整个主 Java 目录。18 个 `SmokeTest/IntegrationChecks/FrameBenchmark/TestStartupDiagnostics` 相关文件占 204,897 / 643,070 字节，约 31.9% 的 Java 源码；六个资源 JAR 也包含这些类。

- 测试/诊断类在每个 JAR 中占约 301–305 kB 未压缩 class 内容。
- 压缩后的相关 class 合计约 138 kB/包，即当前约 1.02–1.04 MB JAR 的 13%左右。
- 六套包合计约 0.83 MB（十进制），尚未扣除分离后需要的最小测试挂接层。
- `UnboxClient.java:41–43` 每 tick 进入多个测试方法，通常被测试开关立即挡住；`FrameBenchmarkMixin` 每帧调用基准入口。

建议把测试类放进独立测试源集/JAR，发布构建不注册测试 Mixin、不调用测试 tick；测试构建使用同一份生产功能 class。验证包和发布包之间仅允许测试钩子差异，记录生产 class 的哈希一致性，避免“测试的是另一套实现”。不承诺这项必然显著提升 FPS。

## 7. 运行效率：有依据的优化候选

1. **配置同步。** `ClientIntegrations.java:29` 每 5 tick 解析反射字段/方法并写上游设置；`SurvivalClientMods.java:32` 每 tick 同步若干值。可缓存反射句柄、对未变化值跳过写入。权限切换和上游快捷键防绕过仍须及时检查；Spatial 的双向同步不能退回单向覆盖。
2. **后台轮询。** `main.tsx:50` 每秒读取启动状态，`Social.tsx:12` 每两秒读取好友快照；Rust 和游戏间还有文件桥轮询。可以对未变化快照跳过 React 更新、对隐藏窗口适度降频，后续再评估 Tauri 事件。好友在线保活、邀请接收、取消与超时不能一起停掉。
3. **启动校验峰值内存。** `launcher.rs` 多处整体读入 JAR 计算摘要或复制，而共享模块已经有分块摘要。优先测大整合包准备时间与峰值内存，再替换相同语义的 I/O。保留篡改检测与用户文件保护。
4. **职责与可读性。** 把主界面中的 Profile 创建流程、游戏任务状态、皮肤操作按现有边界拆开；把 `UnboxScreen` 的设置控件/HUD 编辑与浏览布局分开。先删死分支再拆，避免把旧代码搬成更多文件。格式化单独提交，不能与功能删除混在一起。

衡量指标应包括：冷/热启动时间、准备文件耗时、后台 CPU/唤醒次数、游戏帧时间 p95/p99 与 1% low、包体积和构建时间。代码短、文件少、缓存清掉都不能代替这些指标。
